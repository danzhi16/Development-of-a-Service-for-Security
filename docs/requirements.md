# 6. Requirements Specification

Author: Andrey Rudov. Status: draft v0.1, 2026-10-20.

Priority uses MoSCoW: **M** must (mandatory for the final defense), **S** should, **C** could.
Each requirement has an acceptance criterion (AC) that can be checked by a test or a demo.
Use cases UC-1..UC-6 are defined in [architecture.md](architecture.md).

## Functional requirements

| ID | Requirement | Pri | UC | Acceptance criterion |
|---|---|---|---|---|
| FR-01 | The user can create an evaluation run by choosing models, a task set and prompt conditions. | M | UC-1 | POST /runs with 2 models, 15 tasks, 3 conditions returns a run id and status `queued`. |
| FR-02 | The service ships with the 15-task Python set from SecurityEval and LLMSecEval. | M | UC-1 | `GET /tasks` returns 15 tasks, each with a CWE id and source. |
| FR-03 | The user can upload a custom task set in JSONL. | S | UC-1 | Valid file is accepted; a file with a missing `prompt` field is rejected with a 422 naming the line. |
| FR-04 | The service generates code by sending each task to each selected local model. | M | UC-1 | For every (model, task, condition) a stored generation exists with raw response and extracted code. |
| FR-05 | Condition `security_prefix` prepends the configured security instruction. | M | UC-1 | Stored prompt of the prefix condition starts with the configured text, and the baseline prompt does not. |
| FR-06 | Condition `analyser_repair` sends analyser findings back to the model, up to 3 rounds. | S | UC-1 | A task with findings gets at most 3 repair iterations; a task without findings gets none. |
| FR-07 | The service runs Bandit, Semgrep and CodeQL on each generated file. | M | UC-1 | Each generation has one result row per analyser, including analysers that found nothing. |
| FR-08 | Findings are normalised to a common record: analyser, rule id, CWE, severity, line. | M | UC-1 | Every stored finding has a non-null analyser and rule id; CWE is null only when the rule has no mapping, and those are counted. |
| FR-09 | The service computes metrics: share of generations with at least one finding, CWE distribution, per model and per condition. | M | UC-2 | Metrics for a fixture run match a hand-computed table exactly. |
| FR-10 | The service computes agreement between analysers on the same code. | S | UC-3 | Report shows per-pair agreement; fixture with known overlap gives the expected value. |
| FR-11 | The user can view a model ranking by share of insecure outputs. | M | UC-2 | Ranking page lists models sorted by the metric with the number of tasks behind each value. |
| FR-12 | The user can open a generated snippet with its findings highlighted. | S | UC-4 | Snippet view shows code, and each finding is linked to its line. |
| FR-13 | The user can export a report as JSON and CSV. | S | UC-5 | Exported CSV re-imports in a spreadsheet with the same row count as the on-screen table. |
| FR-14 | The user can check a single code snippet (not generated by the service) with the analysers. | C | UC-6 | POST /snippets/check returns normalised findings within the NFR-01 limit. |
| FR-15 | The user can follow run progress and see failed jobs with the reason. | M | UC-1 | Run status shows done/total counts; a killed worker job is retried and ends as `done` or `failed` with an error text. |
| FR-16 | Access to the API is limited to authenticated users. | S | all | A request without a token gets 401; with a valid token gets 200. |

## Non-functional requirements

| ID | Category | Requirement | Pri | Acceptance criterion |
|---|---|---|---|---|
| NFR-01 | Performance | Static analysis of one generated Python file (Bandit + Semgrep) takes under 10 s on the reference machine. | S | Median over the 15-task fixture below 10 s. CodeQL is excluded and measured separately. |
| NFR-02 | Security | Generated code is never executed outside a sandbox container without network, with read-only root filesystem and resource limits. | M | Test container tries `curl` and a write to `/`; both fail. |
| NFR-03 | Reliability | A worker crash does not lose a run; unfinished jobs are redelivered. | M | Kill the worker mid-run; after restart the run reaches `done` with all expected results. |
| NFR-04 | Resource use | The full pilot (3 models, 15 tasks, 3 conditions) runs on one machine with one GPU, or through Ollama with quantised models. | M | Documented reference hardware; run completes without out-of-memory errors. |
| NFR-05 | Maintainability | Analysers and model backends are added through an interface without changing the pipeline code. | S | Adding a dummy analyser needs one new file and one registry line (demonstrated in a test). |
| NFR-06 | Reproducibility | A run stores model id, parameters, seed (where supported), prompt text, and analyser versions. | M | Run export contains all of these fields. |
| NFR-07 | Usability | A new user creates a run and reads the ranking without instructions. | S | 3 of 3 test users finish the scenario in under 5 minutes (see [verification plan](verification-plan.md)). |
| NFR-08 | Deployability | The whole stack starts with one `docker compose up`. | M | Fresh clone, documented env file, health endpoint returns 200 within 2 minutes. |
| NFR-09 | Data protection | No secrets in the repository; configuration through environment variables with an example file. | M | Secret scan of the repository reports nothing. |
| NFR-10 | Test coverage | Automated tests cover the normalisation, metrics and queue-retry logic. | S | CI reports tests for these three modules and they pass. |

## Traceability to the project aim

FR-01..FR-08 implement the pipeline objective, FR-09..FR-13 the metrics and reports objective,
FR-14 and FR-16 are extensions. NFR-02 and NFR-03 are the main engineering risks.
