## Problem statement

LLMs are widely used to write code. Empirical studies report that a large share of generated code
is vulnerable: about 40% of Copilot programs in the scenarios of Pearce et al. (2022), and
the same weaknesses in AI-generated code already merged into GitHub projects (Fu et al., 2025).
Open-weight models (Llama, Qwen-Coder, DeepSeek-Coder, Mistral/Codestral) can be run locally
without sending code to a third party, so teams adopt them for privacy reasons. Choosing between
them by security is hard: published benchmarks are separate research scripts, report the effect
for one analyser at a time, and are not packaged for a team to rerun on its own models and tasks
(see [literature review](literature-review.md) and [existing systems](existing-systems-comparison.md)).

## Target users

- Development and DevSecOps teams that choose a code model for internal use.
- Security engineers who want to check AI-generated code before it reaches a repository.
- Researchers and instructors who compare models or prompting techniques.

User needs are still assumptions until the interviews in
[evidence-of-relevance.md](evidence-of-relevance.md) are done.

## Aim

To design and build a service that evaluates the security of code produced by open-weight LLMs
automatically and reproducibly, and presents the result as a comparable report.

## Objectives

1. Analyse existing research and tools and fix the evaluation method (literature, comparisons).
2. Specify requirements and design the architecture.
3. Implement the pipeline: task input, code generation by several local models, static analysis
   with several analysers, normalisation of findings to CWE.
4. Implement metrics and reports: share of insecure outputs, CWE distribution, model ranking,
   analyser agreement.
5. Implement the API and web UI.
6. Verify the service on public Python benchmarks (SecurityEval, LLMSecEval) and compare it with
   a manual baseline.

## Expected outcomes

- Running service with REST API and web UI, deployable with Docker Compose.
- Evaluation of at least three open-weight models on at least 15 Python tasks (the course pilot
  already covers 15 tasks; the service must reproduce and extend it).
- Documentation: architecture, API, user guide; thesis chapters.

## Scope

In scope:

- Python code, single-function tasks from public benchmarks and user-supplied tasks.
- Open-weight models served locally through vLLM or Ollama.
- Static analysers Bandit, Semgrep, CodeQL.
- Three prompt conditions: baseline, security prefix, repair driven by analyser feedback.
- Reports per model, per CWE, per prompt condition.

Out of scope (non-goals):

- Languages other than Python (C/C++ and Java are future work).
- Repository-level evaluation that needs full project builds.
- Executing the generated code to confirm exploitability in the MVP (open question for the supervisor,
  see [risks](project-management.md)).
- Training or fine-tuning models.
- Proprietary hosted models as evaluation targets.

## Engineering complexity

The project combines serving several LLMs on limited GPU resources, a job queue for long-running
work, untrusted code handled in a network-isolated environment, aggregation of three analysers with
different output formats, normalisation to CWE, and a statistical method for comparing proportions.

## Relation to the course research project

The course research (Research Methods) studies whether security prompting transfers to open-weight
models, using a script and Bandit. The diploma turns that one-off script into a service. The research
design (three prompt conditions, three analysers, hypotheses H1-H3) is reused as the evaluation method.
